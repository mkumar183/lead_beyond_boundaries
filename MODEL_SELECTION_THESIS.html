Choosing the Right Model for the Right Job

A cost-and-effectiveness study of Opus 4.8, Opus 4.7, and Sonnet 4.6 for software teams — with tooling guidance for GitHub Copilot and Claude Code.

Document type: Research thesis & decision framework
Audience: Eng leaders, staff engineers, platform teams
Models studied: Opus 4.8 · Opus 4.7 · Sonnet 4.6
Tools studied: GitHub Copilot · Claude Code
Scope: Features, bug fixes, prototypes, full apps, E2E, security
Status: v1.0 — living document

Abstract

Large language models are no longer a single-purchase decision. A modern engineering organization runs a portfolio of models, routing each unit of work to the cheapest model that can complete it reliably. This thesis compares three representative tiers — Opus 4.8 (frontier reasoning), Opus 4.7 (prior frontier), and Sonnet 4.6 (high-throughput workhorse) — across two axes that actually appear on an invoice and in a retrospective: token spend and effectiveness (first-pass success, autonomy, review burden).

We map nine common engineering workloads — daily bug fixes, small features, prototypes, full applications, end-to-end test suites, vulnerability remediation, user-story drafting, refactors, and code review — to the model and tool that maximize value per dollar. The central finding: Sonnet 4.6 should carry the majority of daily volume, while Opus-tier models are reserved for ambiguous, high-blast-radius, or security-critical work where a single avoided defect outweighs many multiples of token cost. Tool choice (Copilot vs Claude Code) is orthogonal and complementary: Copilot wins inner-loop velocity, Claude Code wins autonomous multi-file execution.

§1Introduction & Scope

For two decades the build-vs-buy and language-vs-framework debates dominated engineering strategy. A new axis now sits alongside them: which model, via which tool, for which task. Unlike a framework choice, this decision is made dozens of times a day, often implicitly, by every engineer — and each choice has a metered cost and a measurable quality outcome.

This thesis treats model selection as a portfolio optimization problem. The objective function is not "use the smartest model" but "maximize merged, defect-free work per dollar, including human time." We study three model tiers and two tools, and we produce an actionable routing matrix.

In scope

  • Relative token economics across Opus 4.8, Opus 4.7, and Sonnet 4.6.
  • Effectiveness dimensions: first-pass success, autonomy/steps-to-done, review burden, hallucination/regression risk.
  • Nine concrete engineering workloads and their ideal model + tool pairing.
  • When to use GitHub Copilot vs Claude Code, and how they coexist.

Out of scope

  • Exact, dated vendor list prices (volatile — see methodological note).
  • Non-coding workloads (marketing, support, data labeling).
  • Self-hosted / open-weight models — a worthy but separate study.

§2Methodology

We evaluate each model–task pairing along a consistent rubric so the routing matrix is reproducible rather than anecdotal.

Key reframe Total Cost of Resolution (TCoR) = token cost + human review cost + cost of escaped defects. For most teams the token line is the smallest of the three. A model that costs 5× more in tokens but halves review time and defect escapes is frequently the cheaper choice in TCoR.

The TCoR formula we use

TCoR = (tokens_in · price_in + tokens_out · price_out) + (review_minutes · loaded_eng_rate) + (P(escaped_defect) · cost_per_incident) Routing rule: pick the model that MINIMIZES TCoR for the task, not the one that minimizes token cost alone.

§3The Three Models at a Glance

Opus 4.8

Frontier · Deep Reasoning
  • Best multi-step reasoning & long-horizon planning
  • Strongest on ambiguous, under-specified problems
  • Highest token price; highest latency
  • Lowest defect-escape rate on hard tasks

Opus 4.7

Prior Frontier · Fallback
  • Near-frontier reasoning at a modest discount
  • Useful as a stable regression/repro baseline
  • Good when 4.8 is rate-limited or queued
  • Diminishing returns vs 4.8 on the hardest tasks

Sonnet 4.6

Workhorse · High Throughput
  • Excellent speed/cost for well-scoped work
  • Strong everyday coding, edits, tests, docs
  • Cheapest per task; best for high volume
  • Needs tighter prompts on ambiguous problems
Mental model Think Sonnet 4.6 = senior engineer doing the bulk of the sprint, Opus 4.8 = principal engineer you pull in for the gnarly design review, and Opus 4.7 = the principal's equally-capable colleague you call when the first is in a meeting (or when the bill matters more than the last 2% of capability).

§6Cost-Effectiveness Synthesis

Combining §4 and §5: the winning model is the one furthest "up and to the left" — high effectiveness, low TCoR — for a given task class. There is no single winner; there is a winner per task.

Recommended routing pattern Start cheap, escalate on evidence. Attempt with Sonnet 4.6 first. If it fails an automated check (tests, types, lint) or the task is pre-classified as high-ambiguity/high-risk, escalate to Opus 4.8. Log the escalation rate — a rising rate is a signal to refine prompts or task scoping, not necessarily to change models.

§8Scenario Deep-Dives

8.1 — The daily bug-fix factory

A team closes 30–50 small bugs/week. These are localized, have a clear repro, and pass/fail is decided by existing tests. Use Sonnet 4.6 in Copilot. The inner-loop latency matters more than raw intelligence; the tests are your safety net. Reserve Opus only for the 1–2 "mystery" bugs/week where the root cause is non-obvious.

8.2 — Building a prototype in two days

Speed and exploration dominate; throwaway code is acceptable. Drive with Claude Code on Sonnet 4.6 for rapid scaffolding, escalating to Opus 4.8 at the 2–3 genuine architectural forks (data model, auth strategy, async boundaries). Don't pay frontier prices to generate boilerplate.

8.3 — Standing up an entire application

This is a two-phase job. Phase 1 (design): Opus 4.8 to define module boundaries, contracts, and the test strategy — decisions that are expensive to reverse. Phase 2 (build): Sonnet 4.6 to implement each module against those contracts, with prompt caching on the shared architecture context. Claude Code is the natural driver for both phases.

8.4 — Generating an E2E suite

E2E tests are repetitive and pattern-driven. Sonnet 4.6 via Claude Code, batch-generating across pages/flows, is the most cost-effective. Cache the page-object/context prefix. Escalate to Opus only to diagnose flaky tests, where reasoning about timing and state pays off.

8.5 — Vulnerability remediation

The asymmetric-risk case. A missed injection or auth flaw can cost orders of magnitude more than any token bill. Use Opus 4.8 for the analysis and patch, run it through Claude Code so it can read the full call graph, and mandate human security review. This is the one workload where defaulting to the cheap model is a false economy.

Anti-pattern "Opus for everything." The single most common cost mistake we observe is routing all traffic to the frontier model "to be safe." This 3–5×'s the bill while improving outcomes only on the minority of genuinely hard tasks. Default cheap, escalate deliberately.

§10Adoption Playbook

A pragmatic rollout for an engineering org standardizing on this portfolio approach.

Phase 1 — Default & baseline (Weeks 1–2)

  • Set Sonnet 4.6 as the org-wide default in Copilot and Claude Code.
  • Instrument token spend per team and per task type from day one.
  • Publish the routing matrix (§7) as a one-page internal cheat sheet.

Phase 2 — Escalation discipline (Weeks 3–6)

  • Define the explicit triggers for Opus 4.8: security, ambiguity, cross-cutting refactor, novel design.
  • Add "start-cheap, escalate-on-failed-check" to CI-assisted agent workflows.
  • Track escalation rate; investigate teams above/below the norm.

Phase 3 — Optimize (Weeks 7+)

  • Turn on prompt caching for large shared contexts; move non-urgent generation to batch mode.
  • Review TCoR by task type quarterly; rebalance defaults as model quality/price shifts.
  • Keep Opus 4.7 configured as a fallback for rate limits and as a regression baseline.

§12Conclusion

Model selection is a portfolio decision, made many times a day, with money and quality on the line each time.

The evidence points to a clear operating doctrine: make Sonnet 4.6 the default workhorse for the large majority of well-scoped engineering work; escalate to Opus 4.8 deliberately when ambiguity, scope, or security risk make deep reasoning worth its premium; and keep Opus 4.7 in reserve as a fallback and reproducible baseline. Pair this with the right tool — Copilot for the inner loop, Claude Code for the outer loop — and you capture most of the available value at a fraction of the "Opus-for-everything" cost.

The goal is not to use the smartest model. It is to deliver merged, trustworthy software for the lowest total cost of resolution — and that is almost always a portfolio, never a single model. — Thesis central claim

A.2 — How to localize this thesis to your org

  1. Replace the §4 price table with your contracted rates.
  2. Run 20–50 representative tasks per workload through each model; record first-pass success and review minutes.
  3. Compute TCoR (Figure 2.1) per workload and adjust the §7 matrix.
  4. Encode the resulting routing logic in a thin model-router service or shared config.

A.3 — Glossary

  • MTok — million tokens, the standard pricing unit.
  • TCoR — Total Cost of Resolution: tokens + review time + escaped-defect cost.
  • Inner loop — the edit/run/test cycle inside the IDE.
  • Outer loop — multi-file, cross-cutting, agentic work spanning the repo.
  • Prompt caching — reusing a stable context prefix to cut input cost.
  • Escalation rate — share of tasks promoted from Sonnet to Opus.
