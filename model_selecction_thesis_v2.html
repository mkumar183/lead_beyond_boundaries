Abstract

The question is no longer "should we use AI assistants?" — it is "which model, through which tool, for which specific task?" That routing decision is made dozens of times per sprint by every engineer on your team, and each choice carries a direct cost and a measurable quality consequence.

This thesis provides a rigorous, workload-specific framework for engineering organizations to route tasks across three Claude model tiers — Opus 4.8 (frontier reasoning), Opus 4.7 (prior frontier / fallback), and Sonnet 4.6 (high-throughput workhorse) — and across two complementary tools — GitHub Copilot (inner-loop IDE companion) and Claude Code (agentic, terminal-native executor). We analyse token pricing, output quality, latency, and the often-ignored human review cost to compute a Total Cost of Resolution (TCoR) per workload class. The central finding: approximately 70% of daily engineering volume should default to Sonnet 4.6, while Opus-tier models are reserved for tasks where their extra reasoning depth prevents defects that dwarf their token premium. Tool choice is orthogonal: Copilot wins on inner-loop velocity; Claude Code wins on autonomous multi-file execution.

§1Introduction & Framing

Model selection has become a daily operational decision with real financial and quality consequences.

When LLM assistants were a novelty, any model was the right model. Today an engineering team in active sprint conditions may invoke an AI assistant fifty or more times per engineer per day across completions, PR reviews, test generation, refactors, and documentation. Each invocation has a price tag and a success probability. The difference between routing all of that volume to a frontier model versus a well-chosen workhorse tier is often the largest single line-item on an AI cost report — and it is entirely within the team's control.

The framing we use throughout this thesis is the Total Cost of Resolution (TCoR):

TCoR = token_cost + human_review_cost ← often 3–10× the token cost + P(escaped_defect) × impact ← can dwarf everything else ┌─────────────────────────────────────────────────────┐ │ Routing goal: minimise TCoR per task class │ │ NOT: minimise token cost │ │ NOT: maximise model capability │ └─────────────────────────────────────────────────────┘

Figure 1.1 — Total Cost of Resolution. Token cost is necessary but rarely the dominant term.

An Opus-tier model that one-shots a complex refactor and requires 15 minutes of human review has a lower TCoR than a Sonnet-tier model that needs three retries, two manual corrections, and 45 minutes of review — even if the Sonnet session cost five times less in tokens.

⚠️
Anti-pattern to avoid
"Opus for everything." The single most expensive habit is routing all traffic to the frontier model "to be safe." This multiplies the token bill by 4–5× while improving outcomes only on the ~30% of work that is genuinely hard. Measure your escalation rate — if it exceeds 30% of tasks, investigate the cause before adjusting the model default.

Full Application Scaffold

Opus 4.8 Sonnet 4.6 Claude Code
Building a service or app from scratch. Two explicit phases to maximise quality while controlling cost.

E2E Test Suite Generation

Sonnet 4.6 Claude Code
E2E tests are repetitive and pattern-driven — the highest-value use of batch mode and prompt caching.
1. Build a shared context: page-object definitions, auth helpers, test framework config → cache this prefix 2. Claude Code + Sonnet: batch-generate one test file per user flow 3. Run suite → collect failures → fix individually (Sonnet) 4. Opus 4.8 — Non-negotiable Claude Code
Asymmetric risk: the cost of a missed injection, auth bypass, or secrets leak dwarfs any token bill by orders of magnitude.
1. Opus 4.8 in Claude Code: read full call graph + data flow 2. Classify vulnerability: severity, attack vector, blast radius 3. Generate patch + regression test 4. Run SAST tool in the loop (Claude Code executes it) 5. MANDATORY: human security engineer reviews & approves 6. Never auto-merge security patches ───────────────────────────────────────────── Cost profile: 100% Opus 4.8. No exceptions. Human review required.
🔧

Cross-Cutting Refactor

Opus 4.8 Claude Code
Touching many files, high regression risk, cascading implications. Opus 4.8's long-context reasoning is the primary value driver here.
1. Claude Code: index the full repo for Opus 4.8 2. Opus: map all call sites and data flows affected 3. Opus: plan the refactor as a sequence of safe atomic steps 4. Execute each step with Sonnet; run tests after each 5. Opus 4.8 for final review of the complete diff ───────────────────────────────────────────── Cost profile: ~40% Opus (planning + final review), ~60% Sonnet (execution).

§12Adoption Playbook

A pragmatic, three-phase rollout for an engineering organisation standardising on this portfolio approach.

1

Set the default and baseline (Week 1–2)

Configure Sonnet 4.6 as the org-wide default in both Copilot and Claude Code. Instrument token spend per team and per workload type from day one. Publish the §7 routing matrix as a laminated one-pager at every desk (or pinned in every Slack channel).

2

Define escalation triggers explicitly (Week 1–2)

Write down — in a shared config and a team norm — exactly what qualifies as an Opus 4.8 task: security changes, ambiguous cross-cutting work, novel algorithm design, tasks that fail CI twice. Remove the ambiguity that leads to reflexive Opus usage.

3

Add "start-cheap, escalate-on-failure" to CI (Week 3–4)

In agentic Claude Code workflows, encode the routing rule: attempt with Sonnet; if automated checks fail twice, automatically switch to Opus 4.8. Log every escalation. A rising escalation rate is a prompt quality problem, not a model problem.

4

Enable prompt caching for shared contexts (Week 3–5)

Identify the 3–5 large, stable context prefixes used repeatedly (system prompt, architecture doc, shared test fixtures). Enable prompt caching on each. This is typically the highest-ROI cost reduction available after routing policy.

5

Move bulk async jobs to batch mode (Week 4–6)

E2E test generation, large documentation runs, bulk refactor planning — these are non-urgent and can run overnight in batch mode at ~50% discount. Identify your top 3 recurring batch-eligible tasks and configure them.

6

Review TCoR quarterly and rebalance (Ongoing)

Model capability and pricing shift rapidly. Every quarter, review TCoR by workload type. If Sonnet has improved on a task class where you were using Opus, move the routing rule. If a new model tier arrives, evaluate it against the same rubric before adopting.

7

Track the human review cost, not just tokens (Ongoing)

Add a lightweight review-time log to your workflow. Even rough estimates (15 min vs 45 min to verify a change) will reveal which model/workload combinations have hidden costs that token dashboards miss entirely.

§13Risks & Governance

🚨 Reflexive Opus usage

Teams default to the frontier model "to be safe," inflating the bill 4–5× with no quality gain on routine tasks.

Mandate Sonnet default; require logged justification for Opus escalation; monitor model-mix dashboard weekly.

⚡ Under-modelling hard tasks

Using Sonnet for genuinely ambiguous or high-blast-radius work increases defect-escape rate and review burden, negating the token saving.

Publish clear escalation triggers; add auto-escalation rule in CI-integrated agentic workflows.

🔓 Security over-trust

Treating AI-generated security patches as production-ready without human review. Opus 4.8 reduces risk; it does not eliminate it.

All security changes require human security-engineer sign-off. Never auto-merge. Run SAST in the loop regardless of model.

💸 Runaway agentic spend

Long Claude Code sessions with Opus 4.8 and large contexts can generate surprise bills. Especially risky in overnight autonomous runs.

Set per-task token budgets in Claude Code config. Enable spend alerts. Use batch mode for non-urgent large jobs.

📉 Pricing / score drift

This thesis uses representative figures. Vendor pricing and model benchmark scores change quarterly; stale routing rules over- or under-spend.

Quarterly TCoR review cadence (see §12, step 6). Treat the routing matrix as a living document, not a one-time decision.

🔗 Vendor lock-in

Tight coupling to one vendor's model naming or API surface makes model swaps painful when the market evolves.

Abstract model identity behind a thin router layer. Use capability labels ("workhorse", "reasoning", "frontier") not model names in business logic.

§14Conclusion

Model selection is not a one-time decision. It is a daily operating policy with compounding financial and quality consequences.

The evidence assembled across twelve sections converges on three durable conclusions:

  1. Make Sonnet 4.6 the default, not the fallback. Approximately 70% of daily engineering volume — bug fixes, features, tests, stories, documentation, PR reviews — is fully and efficiently served by the workhorse tier. Defaulting to Opus for these tasks is not caution; it is waste.
  2. Escalate to Opus 4.8 deliberately and measurably. Security analysis, ambiguous architecture decisions, cross-cutting refactors, and novel algorithm design are the tasks where frontier reasoning depth converts into avoided defects that dwarf the token premium. Keep Opus 4.7 as the calibrated fallback when 4.8 is unavailable or the last increment of reasoning isn't worth the cost.
  3. Tool and model are orthogonal — run both. Copilot is the high-frequency, low-ceremony inner-loop companion; Claude Code is the autonomous, whole-repo outer-loop executor. They serve different parts of the engineering day and are more powerful together than either is alone.
The goal is not to use the most powerful model. It is to deliver merged, trustworthy, defect-free software at the lowest total cost of resolution — and that optimum is almost always a portfolio of models and tools, routed by task signal, not by instinct. — Closing statement, Model Selection Thesis v2

A.1 — How to localise this thesis to your organisation

  1. Replace the §3 price table with your contracted rates from the billing console.
  2. Select 15–20 representative tasks per workload class and run them through each model tier. Record first-pass success rate, retry count, and human review time.
  3. Compute TCoR per workload using the formula in §1 and your actual loaded engineer rate.
  4. Adjust the §7 routing matrix to reflect your TCoR results, not the generic defaults here.
  5. Encode the resulting routing logic in a shared team config file, CI pipeline env var, or thin router service.
  6. Set a quarterly calendar reminder to re-run steps 1–4.

A.3 — Glossary

  • MTok — million tokens; standard pricing unit.
  • TCoR — Total Cost of Resolution: token cost + human review cost + expected escaped-defect cost.
  • Inner loop — the edit/run/test cycle inside the IDE, where Copilot excels.
  • Outer loop — multi-file, cross-cutting, agentic work spanning the repository, where Claude Code excels.
  • Prompt caching — reusing a stable context prefix (system prompt, architecture doc) to cut input token cost by 50–90%.
  • Batch mode — async, non-priority API calls processed at ~50% of standard price.
  • Escalation rate — share of tasks promoted from Sonnet to Opus tier; a key monitoring metric.
  • Agentic run — a Claude Code session where the model plans, executes, and iterates without per-step human approval.
  • Frontier model — the most capable, most expensive tier; currently Opus 4.8.
